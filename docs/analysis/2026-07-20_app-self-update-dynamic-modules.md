# YiW 自动更新与动态模块能力分析

日期：2026-07-20

## 结论

可以做，而且这很适合 YiW 的产品方向。

但需要把两种“更新”分开：

1. **App 版本更新**：开发者发布新版本后，用户的 YiW 自动下载并安装。这是普通的软件升级。
2. **用户自己的功能更新**：用户说“在侧边栏添加一个股票模块”，YiW 为这个用户生成、预览并安装一个模块。这是个人功能扩展。

第二种不应该直接修改 YiW 自己的核心代码。更稳的做法是：核心 App 保持稳定，用户的新功能以“模块”形式安装。这样既能一句话生成，也能卸载、升级和退回旧版本。

## 当前项目的真实情况

YiW 已经有一部分基础能力：

- WorkspaceAgent 可以在当前工作区读写文件、修改文件和执行命令。
- 写文件和执行命令已经有确认机制。
- App 已经有 Skill 和 MCP，能增加 Agent 的做事方法，也能连接外部服务。
- Electron 页面已经开启 `contextIsolation`，并关闭 `nodeIntegration`，基础隔离方向是正确的。

但当前还不能直接完成“说一句就让侧边栏长出股票模块”：

- 左侧栏由 `YiWShell` 和 `YiWNav` 固定渲染，没有读取动态模块列表。
- 页面路由来自固定的 `viewModules` 和 `constantRoutes`。
- Agent 的文件工具只针对聊天草稿、项目目录或用户打开的文件夹，不负责安装 App 模块。
- Electron 包里没有正式的打包、发布、签名和自动更新配置。
- 当前没有模块清单、模块运行容器、权限说明、预览、版本记录和退回机制。

所以，**当前版本有“生成代码的手”，还没有“把代码安全装进 App 的插槽”**。

## 推荐的产品结构

### 1. 核心 App

核心 App 负责这些稳定能力：

- 对话和 Agent 运行
- 左侧栏和窗口布局
- 模块管理
- 权限确认
- 本地数据存储
- 自动升级
- 模块预览、安装、停用、卸载和退回

核心 App 只能通过正式发布的安装包升级。不要让普通对话直接改正在运行的核心文件。

### 2. 动态模块

每个用户新增的功能都是一个独立模块。模块至少包含：

```json
{
  "id": "stock-center",
  "name": "股票",
  "icon": "chart-candlestick",
  "version": "1.0.0",
  "sidebar": { "visible": true, "order": 20 },
  "permissions": ["network:market-data", "storage:stock-center"],
  "dataProviders": ["market-data-mcp"],
  "minAppVersion": "0.2.0"
}
```

YiW 启动时读取模块清单，自动把模块加入侧边栏。点击后由统一的 `ModuleHost` 打开，不再要求每个模块都写进固定路由表。

### 3. 模块生成器

用户提出要求后，由专门的“模块生成器”处理，而不是让通用 Agent 直接操作 App 安装目录。

模块生成器只应开放少量受控操作：

- 创建模块草稿
- 修改模块草稿
- 检查模块格式
- 运行测试
- 打开预览
- 请求权限
- 安装新版本
- 退回旧版本

这些操作比直接开放任意文件写入和 shell 命令更安全，也更容易查清楚发生了什么。

### 4. 两级模块能力

第一阶段建议只支持**页面描述模块**。模型输出 JSON 页面描述，YiW 用自己内置的表格、卡片、走势图、K 线图、搜索框和列表组件来显示。它覆盖大多数业务模块，而且容易控制质量。

后续再支持**代码模块**。代码模块自由度更高，但必须在隔离环境中运行，限制网络、文件、剪贴板、系统命令和账号凭证。安装包还要有签名和来源检查。

## 股票模块的实际生成过程

用户说：

> 侧边栏添加一个股票模块，这个股票模块参考同花顺进行设计。

YiW 可以按下面的过程工作：

1. 识别需求，默认先做只读版本：自选股、行情、K 线、分时、涨跌榜和提醒。
2. 让用户选择市场和数据来源；信息足够时直接使用合理默认值。
3. 生成模块草稿和权限清单。
4. 在 App 内打开真实预览，使用模拟数据检查布局。
5. 连接行情 MCP 或合规的数据 API，再检查加载、断网、空数据和过期数据状态。
6. 向用户显示“将增加股票侧边栏入口，并访问某个行情服务”，用户确认后安装。
7. 模块立即出现在侧边栏。用户继续说“再加一个筹码分布”时，生成 1.1.0，并保留 1.0.0 供退回。

“参考同花顺”应理解为参考它的信息层次、行情浏览方式和常见操作，不应直接复制界面、图标、文案或品牌。股票数据也必须来自允许使用的数据源，不能抓取或转卖没有授权的数据。

## 自动化边界

推荐达到的体验是：**一句话提出要求，YiW 自动生成、检查和预览，用户确认一次后安装。**

不推荐完全静默地修改和安装，原因包括：

- 模块可能访问网络、文件或账号。
- 股票模块可能进一步涉及券商账号和交易操作。
- 模型生成的界面可能与用户想法不同。
- 出错时需要明确知道改了什么，并能马上退回。

查看行情可以采用普通权限。下单、转账、读取券商账号等能力必须使用单独的高风险权限，每次关键操作都要确认，不能因为用户安装了股票模块就默认开放。

## App 自身的自动更新

这部分使用标准 Electron 更新方式即可：

1. 建立 macOS、Windows 的正式打包流程。
2. 对安装包进行代码签名；macOS 还需要公证。
3. 发布版本文件和更新说明。
4. App 定时检查新版本，在后台下载。
5. 下载完成后提示用户重启安装。
6. 支持分批发布、失败停止和版本退回。

App 自动更新与个人模块互不影响。核心 App 升级后，要根据模块的 `minAppVersion` 和接口版本检查兼容性；不兼容的模块先停用，不要让整个 App 无法启动。

## 建议的开发顺序

### 第一阶段：先让 App 能正常升级

- 完成正式打包、签名、发布和自动更新。
- 明确 App 版本和模块接口版本。

### 第二阶段：建立模块插槽

- 增加模块表和模块清单。
- 左侧栏改为读取动态模块。
- 增加 `ModuleHost`、模块设置、启用、停用、卸载和退回。
- 先只运行 YiW 自带组件拼成的页面描述模块。

### 第三阶段：接入一句话生成

- 增加模块生成器和受控工具。
- 增加预览、自动检查、权限确认和安装流程。
- 用股票模块作为第一个完整样例。

### 第四阶段：开放更强扩展

- 支持隔离的代码模块。
- 支持模块分享、导入和可信来源。
- 增加模块升级兼容检查和故障自动停用。

## 最终建议

YiW 应把这个能力定义为“**会成长的个人工作台**”，而不是“App 自己改自己的代码”。

对用户来说，体验仍然是自然的：说一句话，侧边栏就能增加股票、客户管理、项目看板或运营监控。对系统来说，实际发生的是生成并安装一个有权限、有版本、可预览、可退回的模块。这个边界能同时保留 AI 的灵活性和桌面软件需要的稳定性。
